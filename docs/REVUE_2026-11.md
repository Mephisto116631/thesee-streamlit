## 1. Les échecs non bloquants ne passent plus inaperçus

**Problème.** Dans `publish.publier()`, plusieurs étapes « bonus » sont protégées par un `try/except`
qui se contente d'afficher un message. Ces étapes sont :
- la volatilité prévue ;
- le portefeuille et le stress test ;
- le risque du mois à venir ;
- les comptes SEC ;
- les modèles horizon ;
- le cours EUR/USD.

Le passage était quand même enregistré `success`, et l'appli affichait « à jour ». Une panne pouvait
donc durer des semaines sans se voir.

**Correction.**
- `publish.avertir(msg)` remplace les `print("[PUBLISH][WARN] …")`. Il affiche toujours le message, et
  l'ajoute en plus à `publish.AVERTISSEMENTS`, vidé au début de chaque `publier()`.
- Le résumé renvoyé par `publier()` contient la clé `avertissements`.
- `cron_sync.statut_passage()` choisit le statut du passage :
  - `success` : tout est publié ;
  - `partiel` : un avertissement au moins. Le message de `sync_log` liste alors ce qui a échoué.
- `db.sync_log_end` traite `partiel` comme un passage terminé : progression 100 %, étape « Terminé avec
  avertissements ».
- Côté appli, le nouveau module `mobile/src/sync.ts` fournit `passageTermine`, `libelleStatut` et
  `etatDonnees` :
  - l'accueil affiche « à jour, avec avertissements » au lieu de « à jour » ;
  - « Relancer le calcul » considère un passage `partiel` comme terminé, et montre la liste des
    avertissements sous « Dernier calcul ».
- Le statut `partiel` est ajouté au commentaire de `sync_log.status` dans `supabase_schema.sql`.
  Aucune contrainte SQL ne limitait les valeurs : **rien à migrer**.

**Tests.**
- `tests/test_garde_fous.py` : `test_avertir_collecte_et_statut_partiel` et
  `test_statut_success_sans_avertissement`.
- `mobile/src/sync.test.ts` : 3 tests.

## 2. Plus de suppression massive de titres

**Problème.** Dans `data_pipeline._sync_incremental`, un lot de 100 titres dont le téléchargement
échoue est simplement sauté. Le snapshot était donc incomplet, puis
`db.delete_where_not_in("titres_snapshot", …)` supprimait de l'appli tous les titres absents. La liste de
l'indice peut aussi tomber sur sa liste de secours réduite (`universe.py`), avec le même effet.

**Correction.**
- `publish.titres_a_retirer(existants, a_garder)` calcule les titres à retirer. Il **refuse**
  (`ValueError`) si la suppression toucherait plus de 5 % des titres en base
  (`PART_MAX_SUPPRESSION`, avec un minimum de 10 titres), ou si la liste à garder est vide.
- En cas de refus, rien n'est supprimé, un avertissement est noté et le passage devient `partiel` (§ 1).
  Les titres restent visibles avec leur dernière date, ce qui vaut mieux que de les voir disparaître.
- `db.delete_where_not_in` est remplacé par `db.delete_in(table, colonne, valeurs)`. Cette fonction ne
  fait que supprimer : le choix des lignes et les garde-fous sont faits par l'appelant.

Une vraie sortie de l'indice ne concerne que quelques titres par trimestre, donc bien moins de 5 %.

**Tests.** `test_retire_les_quelques_titres_sortis`, `test_refuse_une_suppression_massive` et
`test_petite_base_tolere_dix_retraits`.

## 3. Des versions figées, et enregistrées avec chaque essai

**Problème.** `requirements.txt` ne fixe aucune version. Le re-test mensuel de l'IA de volatilité
(`experiences.yml`) pouvait donc changer de verdict parce que xgboost, scikit-learn ou pandas avait
changé de version, et non parce que le marché avait changé. C'est contraire à la méthode.

**Correction.**
- Nouveau fichier **`requirements-lock.txt`** : les 87 dépendances (directes et indirectes), aux
  versions résolues pour **Python 3.11 / Linux**, comme dans les workflows.
- Les trois workflows Python (`sync.yml`, `experiences.yml`, `tests.yml`) installent avec
  `pip install -r requirements.txt -c requirements-lock.txt`. Le cache pip suit les deux fichiers.
- `requirements.txt` reste la liste des dépendances **directes**, et le fichier lock les fige.
- Une modification de `requirements-lock.txt` relance aussi le laboratoire sur la PR. On voit ainsi
  tout de suite si une mise à jour change un verdict.
- `experiences._ecrire()` enregistre chaque essai. Il ajoute `diagnostics.versions` (Python, numpy,
  pandas, scipy, scikit-learn, xgboost, shap, yfinance, torch). Les 7 enregistrements de
  `experiences.py` passent désormais par lui.

**Vérification.** Toute la suite de tests passe sous Python 3.11 avec exactement ces versions.

**Mettre à jour les versions** (volontairement, dans une PR à part, pour voir l'effet sur le
laboratoire) :

```bash
pip install --dry-run --ignore-installed --python-version 3.11 --implementation cp \
  --platform manylinux2014_x86_64 --platform manylinux_2_28_x86_64 --platform manylinux_2_17_x86_64 \
  --only-binary=:all: --report rapport.json -r requirements.txt
python -c "import json; r = json.load(open('rapport.json'));
[print(i['metadata']['name'].lower() + '==' + i['metadata']['version'])
 for i in sorted(r['install'], key=lambda i: i['metadata']['name'].lower())]"
```

Il faut garder l'en-tête de commentaires du fichier.

**Limite.** PyTorch (seulement pour le CNN du laboratoire et ses tests) est installé à part, depuis
l'index de PyTorch, et sa version n'est pas figée. Elle est en revanche enregistrée dans
`diagnostics.versions`.

**Test.** `test_versions_enregistrees_dans_les_diagnostics`.

## 4. « Relancer le calcul » réservé aux comptes connectés

**Problème.** La fonction Supabase `relancer-calcul` acceptait tout appel portant la clé anon. Or cette
clé est publique : elle est embarquée dans la PWA publiée sur GitHub Pages. N'importe qui pouvait donc
déclencher la synchronisation toutes les 10 minutes.

**Correction** (`supabase/functions/relancer-calcul/index.ts`).
- Le jeton de l'en-tête `Authorization` doit être celui d'un **utilisateur connecté**. C'est le compte
  de l'onglet Positions, et l'appli envoie déjà ce jeton (`sb.functions.invoke`). Sinon la réponse
  est une 401 : « Connecte-toi (onglet Positions) pour relancer le calcul. »
- Le secret **`RELANCE_EMAILS`** est facultatif : des adresses séparées par des virgules. S'il est
  défini, seuls ces comptes peuvent relancer (réponse 403 pour les autres).
- Les garde-fous existants sont inchangés : pas de relance si un calcul tourne déjà, ni moins de
  10 minutes après le précédent.

**À faire par vous (une fois).**
1. Redéployer la fonction : `supabase functions deploy relancer-calcul`, ou depuis le tableau de bord
   Supabase (Edge Functions).
2. Conseillé : Supabase → Edge Functions → Secrets → `RELANCE_EMAILS` = votre adresse.

Sans redéploiement, l'ancienne version, ouverte à tous, reste en service.

## 7. Relecture automatique et avertissements des tests

- **ruff**, configuré dans `ruff.toml`, est lancé par `tests.yml`. Les règles sont limitées aux vrais
  problèmes : erreurs de syntaxe, noms non définis, imports ou variables inutilisés, redéfinitions. Le
  style n'est pas imposé. Il a déjà trouvé, et ces points sont corrigés :
  - un import inutilisé dans `experiences.py` (`portefeuille`) ;
  - un import inutilisé dans `pages/1_Screener.py` (`pandas`) ;
  - un import inutilisé dans `pages/4_Credit_Bilan.py` (`numpy`) ;
  - une variable calculée mais inutilisée dans un test (`saut`). Le test l'utilise désormais.
- **Avertissements NumPy.** Il y en avait environ 240 avec NumPy 2.5 (« invalid value encountered in
  divide »). Ils venaient de corrélations de rang calculées sur une colonne constante.
  - `modele_horizon._spearman()` renvoie directement NaN dans ce cas. C'est le même résultat qu'avant,
    puisque la date était déjà écartée par `dropna()`, mais sans avertissement.
  - `_ic_par_date`, `_corr_par_date` (`modele_horizon.py`) et `_ic_rangs` (`examen_risque.py`)
    l'utilisent.
- **Avertissement pandas.** `membres_a_date` remplissait les dates de fin vides avec
  `pd.Timestamp.max`, ce que pandas va bientôt refuser. Le filtre s'écrit maintenant
  « fin vide **ou** date < fin », avec le même résultat.

**Test.** `test_spearman_constante_donne_nan_sans_avertissement`.

## 9. Ce qui reste à décider (non fait volontairement)

- **L'avenir de l'app Streamlit** (points 5 et 9).
  - Elle se dit « lecture seule », mais `get_all_data()` garde `entrainer_1j=True` par défaut : chaque
    visite entraîne encore l'ancien XGBoost à 1 jour, jugé non probant.
  - Sa page d'accueil (`app.py`) et ses pages d'audit (`3_Audit_IA.py`, `5_Audit_ETF.py`) reposent
    sur ce modèle. Le désactiver casserait donc ces pages.
  - Deux voies sont possibles :
    - **(a)** abandonner Streamlit (l'APK et la PWA le remplacent) et retirer `streamlit`, `shap`,
      `matplotlib`, `_st_shim.py` et le modèle 1 jour ;
    - **(b)** sortir le calcul de `data_pipeline.py` dans des modules sans `streamlit`, que l'app
      Streamlit appellerait à travers une fine couche d'affichage.

    Les deux suppriment le faux module `streamlit` du cron. Le choix vous revient.
- **Découpage des gros fichiers** (point 6). `examen_risque.py` (1190 lignes) et
  `experiences.lancer_examen` (une chaîne de `if/elif` d'environ 240 lignes) gagneraient à passer par
  un registre `{nom: fonction}`. Ce code n'est vérifié qu'en conditions réelles, avec Supabase et
  plusieurs heures de calcul. Mieux vaut le restructurer dans une PR à part, pendant un mois calme du
  laboratoire.
- **Taux sans risque** (point 9). La valeur de 4,35 % est écrite à trois endroits : `portefeuille.RF`,
  `mobile/src/settings.ts` et `mobile/src/portfolio.ts`. Elle pourrait être lue chaque jour depuis
  FRED (série DGS3MO) par le cron et publiée dans `market_overview`. Mais elle entre dans le
  portefeuille conseillé et dans la fixture partagée : c'est un **choix de méthode**, à écrire d'abord
  dans `METHODE.md` § 2.
- **Code mort** : le modèle 1 jour, `N_CANDIDATS` (gardé pour le backtest comparatif) et les routes
  `#/court` et `#/titres` de l'appli. C'est à traiter avec la décision sur Streamlit.
